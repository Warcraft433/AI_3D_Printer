Chapter 1: Project Overview & Strategic Mission

1.1 Project Identity & Core Purpose

PrintGuard AI is an autonomous, end-to-end additive manufacturing operating platform. It seamlessly connects cloud-based CAD generation, parametric slicing pipelines, real-time computer vision defect monitoring, and direct browser-to-firmware hardware control. The platform transforms 3D printing from an error-prone, manually observed hobbyist workflow into an enterprise-grade, intelligent, self-monitoring manufacturing pipeline.

1.2 The Problem Statement

Fused Deposition Modeling (FDM) 3D printing suffers from an inherent lack of real-time feedback:

  • Spaghetti Failures & Print Detachment: When a print detaches from the print bed, the extruder continues depositing molten filament into mid-air, creating extensive nests of ruined plastic ("spaghetti defect"), wasting up to 500g of material and hours of machine time.
  • Thermal Runaway & Physical Fire Risk: Unmonitored heating elements and mechanical blockages can lead to thermal destruction or dangerous printer failure.
  • Complex, Fragmented Software Toolchain: Operators traditionally toggle between 3D modeling packages (Blender/Fusion360), separate desktop slicing software (PrusaSlicer/Cura), external camera software (OctoPrint/Moonraker), and physical SD card transfers.
  • Lack of In-Browser Direct Hardware Communication: Most modern web systems require intermediate Raspberry Pi nodes running OctoPrint, adding hardware cost and complex network setup.

1.3 The PrintGuard AI Solution

PrintGuard AI unifies the entire lifecycle into a unified, secure web ecosystem:

  1. Generative 3D Modeling Engine: Translates natural language prompts and reference images into manifold 3D models (OBJ/STL) using procedural parametric CAD synthesis and deep learning checkpoints.
  2. Integrated Slicing Engine: Executes PrusaSlicer in headless CLI mode on the server to convert 3D geometry into optimized G-code with custom infill, speed, and support parameters.
  3. Deep Learning Computer Vision Guard: Runs a high-speed YOLOv8/v11 convolutional neural network on streaming camera frames, detecting extrusion failures and print detachment in under 50 milliseconds.
  4. Autonomous Fail-Safe Interlock: When a spaghetti defect or detachment is classified with confidence above threshold (> 0.35), the backend issues an emergency pause command to the printer via WebSocket or OctoPrint REST API, halting extrusion immediately.
  5. Direct Browser-to-Printer Web Serial Control: Leverages the W3C Web Serial API to establish direct USB UART communication from Google Chrome/Edge directly to 3D printer mainboards (e.g., Marlin, RepRap, Klipper) at 115200 or 250000 baud without requiring an external microcomputer.

Chapter 3: System Architecture & Visual Diagrams

3.1 High-Level Architecture Topology

PrintGuard AI is structured as a decoupled multi-tier architecture consisting of five distinct operational planes: the Client Interaction Plane (React/Three.js), the Business Logic Plane (Spring Boot), the AI & Geometry Inference Plane (FastAPI/PyTorch), the Persistence Plane (PostgreSQL & Supabase Storage), and the Physical Hardware Execution Plane (USB Serial & OctoPrint).

Figure 3.1: PrintGuard AI Multi-Tier System Architecture and Inter-Service Communication Topology

3.2 Component Responsibilities

  • Frontend Client (React/Three.js): Provides browser-native 3D model visualization, real-time bounding box overlay on webcam feeds, direct serial UART communication to the 3D printer mainboard via Web Serial API, and interactive layer-by-layer G-code inspection.
  • Backend Engine (Spring Boot 3): Orchestrates business logic, validates and stores print jobs, enforces user ownership, manages PrusaSlicer execution pipelines, handles file downloads/uploads, and broadcasts WebSocket push events.
  • AI Microservice (FastAPI/PyTorch): Executes YOLOv8 object detection on camera frames with low latency, classifies defects (spaghetti vs normal extrusion), and exposes parametric CAD mesh generation.
  • Persistence Layer (PostgreSQL & Supabase): Stores transactional job records, audit events, user credentials, and error log entities. Protected by PostgreSQL Row Level Security (RLS) policies.
  • Hardware Execution Layer: Physical 3D printer (e.g. Ender 3, Prusa i3 MK3S, Voron) driven either directly from the browser via Web Serial API or via OctoPrint over local LAN.

Chapter 5: Features & Functional Workflows

This chapter details every existing feature across the 10 mandated architectural dimensions, tracing the end-to-end data journey from user interaction to hardware output.

Feature 1: User Authentication & Role-Based Access Control

1. Description: Secure registration, login, JWT issuance, token refresh, and user profile management.

2. Rationale: Protects printer hardware, proprietary 3D CAD files, and multi-tenant job queues from unauthorized access.

3. User Access: Routes /login and /register; account settings accessed from user badge in header.

4. Frontend: Login.jsx, Register.jsx, and AuthContext.jsx managing token persistence in localStorage.

5. Backend: AuthController.java, JwtService.java, PasswordService.java, JwtAuthenticationFilter.java.

6. Database: Table auth_user storing hashed passwords, username, email, is_superuser, is_active flags.

7. APIs: POST /api/auth/login, POST /api/auth/register, GET /api/auth/me, POST /api/auth/refresh.

8. Validation: Argon2/jBCrypt password hashing; username uniqueness enforced at database level; JWT signed with HMAC-SHA256.

9. Dependencies: Spring Security Filter Chain; required by all protected API routes.

10. Limitations & Improvements: Refresh token rotation is single-token; add OAuth2 / Social Login (Google/GitHub) in future.

Feature 2: Text-to-3D Generative Procedural CAD Engine

1. Description: Generates watertight 3D manifold meshes (OBJ/STL) from natural language prompts.

2. Rationale: Allows non-engineers to create functional 3D printable objects instantly without complex CAD software.

3. User Access: Route /generate accessible via the navigation sidebar.

4. Frontend: GenerateModel.jsx with prompt input, steps slider, 3D preview canvas, and generation status indicator.

5. Backend: GenerationController.java calling FastAPI /api/geometry/generate with fallback to local Python script.

6. Database: Table generated_models_generatedmodel saving prompt, file_path, status, generation_time, and user_id.

7. APIs: POST /api/generate/text, GET /api/models/{id}, GET /api/models/{id}/file.

8. Validation: Manifoldness check (watertight geometry verification); mesh volume > 0; sanitized filename generation.

9. Dependencies: Python geometry engine (chess_generator.py); Supabase/Local storage for file persistence.

10. Limitations & Improvements: Procedural engine covers chess and geometric primitives; neural Shap-E requires GPU server.

Feature 3: PrusaSlicer Headless Slicing Pipeline

1. Description: Transforms raw 3D meshes (OBJ/STL) into optimized, layer-by-layer G-code toolpaths.

2. Rationale: Automated slicing on the server removes the need for users to install and configure desktop slicers.

3. User Access: "Slice Model" button on any model card in ModelHistory.jsx or upon completing generation.

4. Frontend: Modal dialog in ModelHistory.jsx for selecting layer height (0.15mm - 0.30mm), infill percentage (15% - 100%), and support structures.

5. Backend: SlicerService.java and PrintJobController.java executing PrusaSlicer CLI with configured arguments.

6. Database: Table print_jobs_printjob tracking gcode_path, estimated_time, progress, and status.

7. APIs: POST /api/jobs/create with payload containing model_id, layer_height, and infill.

8. Validation: Slicer process timeout watchdog (90 seconds); G-code output existence and non-zero byte size validation.

9. Dependencies: Installed PrusaSlicer binary on server (Windows prusa-slicer-console.exe or Linux prusa-slicer).

10. Limitations & Improvements: Limited to single-extruder configurations; future support for multi-material (MMU) slicing.

Feature 4: Three.js Interactive 3D G-Code Visualizer

1. Description: Real-time 3D canvas rendering of G-code toolpaths with layer-by-layer scrubbing and travel move analysis.

2. Rationale: Verifies print integrity, overhang angles, and support placement before sending commands to physical hardware.

3. User Access: Route /gcode-preview or clicking "Preview Toolpaths" on any sliced job.

4. Frontend: GCodePreview.jsx using Three.js LineSegments, orbit controls, custom layer slider, and extrusion speed coloring.

5. Backend: StorageController.java streaming G-code files with byte-range support.

6. Database: Read access to print_jobs_printjob to fetch G-code URL.

7. APIs: GET /api/jobs/{id}/gcode or authenticated signed storage URL.

8. Validation: Client-side G-code parser filters invalid coordinate tokens (NaN/Infinity) and verifies extrusion dimensions.

9. Dependencies: Three.js WebGL canvas context.

10. Limitations & Improvements: Large G-code files (> 50MB) can cause browser memory pressure; implement Web Workers for background parsing.

Feature 5: Direct Hardware Printer Control via Web Serial API

1. Description: Browser-native direct USB serial connection to 3D printer mainboards without needing OctoPrint or Raspberry Pi.

2. Rationale: Eliminates extra hardware costs ($50-100 for a Raspberry Pi) and enables instantaneous machine control.

3. User Access: Route /control ("Printer Control" in sidebar).

4. Frontend: PrinterControl.jsx using navigator.serial.requestPort(), ReadableStream, and WritableStream.

5. Backend: Operates entirely peer-to-device from the client; status sync sent to backend via WebSocket.

6. Database: Audit log recorded in print_jobs_auditlog upon critical manual jog or emergency stop actions.

7. APIs: W3C Web Serial API standard; optional REST telemetry sync POST /api/jobs/{id}/telemetry.

8. Validation: Baud rate selection (115200 or 250000); G-code checksum validation; serial port disconnection listeners.

9. Dependencies: Chromium-based browser (Google Chrome, Microsoft Edge, Brave, Opera) with Web Serial support.

10. Limitations & Improvements: Not supported on Firefox or Safari (W3C standard not implemented by Mozilla/Apple); display clear browser compatibility banner.

Feature 6: Real-Time AI Computer Vision Defect Monitoring

1. Description: Continuous video frame analysis using YOLOv8 to detect printing defects (spaghetti, detachment) with autonomous interlock.

2. Rationale: Protects against catastrophic failure, saves filament, and prevents hardware damage when unattended.

3. User Access: Route /monitoring ("AI Monitoring" in sidebar).

4. Frontend: AIMonitoring.jsx rendering HTML5 video element, canvas overlay with bounding boxes, confidence meter, and auto-pause switch.

5. Backend: ErrorLogController.java and OctoPrintService.java coordinating automatic pause actions.

6. Database: Table error_logs_errorlog storing error_type, confidence, action_taken, timestamp, and frame_image.

7. APIs: POST /api/inference/detect-frame, GET /api/logs/errors, POST /api/jobs/{id}/pause.

8. Validation: Confidence threshold filtering (> 0.35); allow-list filtering preventing spurious food classes from triggering false alarms.

9. Dependencies: FastAPI microservice running ai-model/best.pt with OpenCV and PyTorch.

10. Limitations & Improvements: Single-camera viewpoint; add multi-angle camera support and temporal smoothing across consecutive frames.

Chapter 6: Backend Engineering & REST/WebSocket API Reference

6.1 Backend Architecture & Layered Design

The backend is developed in Java 21 using Spring Boot 3.3.0. It follows a strict 4-layer architecture:

  • Controller Layer: Handles HTTP request serialization, path variables, query parameters, and security context extraction.
  • Service Layer: Encapsulates business logic, file system operations, PrusaSlicer process execution, and external REST calls.
  • Repository Layer: Spring Data JPA interfaces extending JpaRepository with custom derived queries.
  • Entity Layer: JPA entities annotated with Hibernate mappings, cascading relationships, and table constraints.

7.2 Web Serial API Direct Printer Communication Protocol

The PrinterControl.jsx component communicates directly with the printer's 8-bit or 32-bit microcontroller (e.g., ATmega2560, STM32, RP2040) over USB serial UART: 

// 1. Request user permission to connect to USB serial device
const port = await navigator.serial.requestPort();
await port.open({{ baudRate: 115200 }});

// 2. Continuous reader loop decoding printer response stream
const textDecoder = new TextDecoderStream();
const readableStreamClosed = port.readable.pipeTo(textDecoder.writable);
const reader = textDecoder.readable.getReader();

while (true) {{
    const {{ value, done }} = await reader.read();
    if (done) break;
    // Parse temperature reports: "ok T:215.4 /215.0 B:60.1 /60.0"
    parsePrinterFeedback(value);
}}

// 3. Command writer sending G-code instructions
const encoder = new TextEncoder();
const writer = port.writable.getWriter();
await writer.write(encoder.encode("G28\n")); // Auto-home all axes
writer.releaseLock();

8.2 Supabase Row Level Security (RLS) Implementation

Flyway migration V2__enable_rls_and_least_privilege.sql enforces multi-tenant security directly inside PostgreSQL:

  • ALTER TABLE auth_user ENABLE ROW LEVEL SECURITY;
  • ALTER TABLE generated_models_generatedmodel ENABLE ROW LEVEL SECURITY;
  • ALTER TABLE print_jobs_printjob ENABLE ROW LEVEL SECURITY;
  • ALTER TABLE error_logs_errorlog ENABLE ROW LEVEL SECURITY;
  • ALTER TABLE print_jobs_auditlog ENABLE ROW LEVEL SECURITY;

Policies ensure that non-superusers can only SELECT, UPDATE, or DELETE records where user_id = auth.uid() or where parent print jobs belong to the authenticated principal.

Chapter 13: Security Architecture, Authentication & Fail-Safe Controls

13.1 Defense-in-Depth Security Model

  • Cryptographic Password Protection: Passwords are never stored in plain text. Argon2id / jBCrypt hashes with adaptive salt prevent dictionary and rainbow-table attacks.
  • Stateless JWT Authentication: HMAC-SHA256 tokens contain user ID and expiration claims. The server signs each token with PRINTGUARD_JWT_SECRET.
  • Internal Microservice Tokens: The FastAPI AI service enforces an internal secret token (X-Internal-Token) in production environments to prevent unauthorized inference invocation.
  • PostgreSQL Row Level Security (RLS): The database layer strictly validates that queries only operate on data owned by the authenticated tenant.
  • Physical Hardware Fail-Safe Interlock: When defect confidence exceeds threshold, the software automatically triggers printer pause to eliminate fire hazards and filament waste.

Chapter 17: Future Change & Modification Guide (Developer Handbook)

17.1 Step-by-Step Feature Implementation Protocol

Future software engineers or AI coding agents modifying PrintGuard AI must follow this rigorous change protocol:

  1. Identify Impact Radius: Determine whether the change affects the Database (Flyway migration required), Backend (Spring Boot entity/controller), AI service (FastAPI endpoint), or Frontend (React component).
  2. Preserve Database Integrity: Never run manual ALTER TABLE commands directly on production. Create a new numbered migration file in backend-java/src/main/resources/db/migration/ (e.g., V3__add_new_feature.sql).
  3. Maintain Backward Compatibility: Ensure older REST API response formats remain compatible with existing mobile or web clients.
  4. Execute Automated Tests: Always run ./mvnw test and pytest before committing any modifications.
  5. Update Documentation: Reflect API, schema, or configuration variable updates in this Master Documentation.
